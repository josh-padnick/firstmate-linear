---
title: Metrics
description: Measure the attention FM Linear asks of Firstmate, alongside delivery delays and unresolved work.
---

FM Linear should help you see whether the integration is consuming too much of Firstmate's attention.
A useful summary shows how often it asks questions, how often it notifies Firstmate, and whether those interruptions help move work forward.
Measure delays and unresolved requests alongside notification volume so quieter operation does not hide stalled work.

## Separate your requests from integration overhead

A comment from the captain is work you asked Firstmate to handle.
A question generated by FM Linear to clarify a task's outcome is integration overhead.
Metrics distinguish those origins and separate feedback, approvals, routine clarification, and recovery messages.

A saved request, an emitted notification, and an agent response are different events.
Several questions can be combined into one notification, and one unanswered question can cause repeated notifications.
A notification count measures activity on the delivery interface; it does not prove Firstmate read the message or spent a full agent turn on it.
When notification emission cannot be observed, show it as unavailable rather than counting a queued request as a confirmed notification.

## What to measure

| Metric | Meaning |
| --- | --- |
| Integration requests per active task | Distinct integration-generated requests first sent during the period, divided by distinct tracked tasks with observed activity during that period. Count execution retries under the same task once in the denominator. |
| Notifications per monitored hour | Observed notifications emitted to Firstmate, divided by the hours for which notification observation was available. Show captain-originated, integration-generated, and mixed batches separately. |
| Repeat notifications | Additional notifications containing a request that was already sent and remains unresolved. Distinguish scheduled reminders from delivery retries. |
| Questions resolved without contacting Firstmate | Recorded information gaps resolved from task records or other existing evidence before any request was sent. Count actual tracked gaps, not hypothetical questions avoided. |
| Questions per notification | Distinct requests included in each emitted notification. This shows whether batching reduces interruptions. |
| Report-request turnaround | Time from the first notification of a report request to acceptance of an adequate report. Show pending request count and age alongside completed turnaround times. |
| Attributable input and output tokens | Usage explicitly associated with servicing integration requests, when Firstmate exposes reliable request-level attribution. Otherwise show it as unavailable. |

Show the raw counts, time window, and observation coverage alongside rates.
If there are no active tasks or no monitored hours, the corresponding rate is unavailable rather than zero.
For turnaround comparisons, group requests by when they were first notified and retain the unresolved members of that group.
A missing or incomplete report must not disappear from the summary just because it has no completed duration.

Do not assign all of a worker's token usage to FM Linear simply because the worker received an integration message.
Token counts also do not directly measure interruption cost or the usefulness of the work.

## Metrics by integration activity

| Integration activity | Measurements and detail |
| --- | --- |
| Read Linear updates and Firstmate state | Poll/query attempts, successes and failures, operation duration, and observation availability. Routine reads do not count as messages or notifications. |
| Prepare a task brief | Preparation results and duration, verified launch coverage, and recovery requests. See [task-brief metrics](/reference/firstmate/#metrics-for-task-brief-preparation). |
| Send feedback, approvals, or worker instructions | Input counts, handoff delays, pending age, observed notifications, and retries, separated by origin and destination. See [message activity metrics](/reference/messages/#metrics-for-other-message-activities). |
| Request an outcome report | Gaps resolved without contact, requests sent, batching, repeats, report results, turnaround, and unresolved age. See [report-request metrics](/reference/messages/#metrics-for-report-requests). |
| Publish Linear replies, fields, links, or dependencies | Attempted and confirmed writes, retries, failures, and pending update count and age. A publication is not an interruption of Firstmate. |

These operational measurements help explain attention metrics.
For example, increasing clarification requests alongside failed state queries suggests an observation problem; failed brief preparation followed by corrective messages suggests a preparation problem.
Such patterns guide investigation rather than establish the cause on their own.

Count a shared request once even when it appears in both an activity-specific view and an overall summary.
For preparation coverage, report matching, mismatched, and unknown observed launches separately; the verified rate is matches divided by matches plus confirmed mismatches.
Also show the unknown count and observation coverage, so that rate is not presented as coverage of every dispatch.

## Reading a summary

An illustrative weekly summary might say:

> 40 active tasks; 12 integration-generated questions sent in 6 notifications.
> One of those questions needed a repeat notification.
> Another 18 recorded information gaps were resolved from task records before contacting Firstmate.

These are example numbers, not measurements from this installation.
A useful summary also shows how many questions remain unanswered, their ages, and whether delivery delays increased.
Filter by Firstmate home, task, request reason, and workflow stage to find where most of the overhead comes from.

Start by observing normal usage rather than setting an arbitrary noise target.
A growing repeat-notification count suggests a different problem from many distinct, useful questions.
Lower notification volume is helpful only if important requests still reach Firstmate and work continues to progress.

## Where the data lives

FM Linear owns the measurements and stores a lightweight event history in its existing local SQLite database.
No separate metrics database or hosted telemetry service is required.
Code records events as part of normal synchronization; collecting metrics should not create additional messages or model calls.

Records contain identifiers, event kinds, reasons, timestamps, batch membership, and outcomes.
Metrics do not need copies of full prompts, comment bodies, credentials, or private artifacts.
Storage retention must preserve pending requests and the delivery identities needed for safe retries.
Summaries should identify gaps in retained history or observation coverage.

## Keeping the integration quiet

Read existing evidence before asking Firstmate, and allow a short settling period for a completion report to arrive.
Ask only when a missing fact prevents a meaningful integration action.
Keep one outstanding request for that fact and execution attempt, and combine nonurgent questions for the same Firstmate home.
Prioritize captain feedback, approvals, and pause or cancellation requests.

Receiving a request and resolving it are separate milestones.
Track the outstanding question without treating every poll as a reason to notify Firstmate again.
Bound reminders, preserve unresolved requests, and make persistent problems visible.
Routine successful synchronization should remain quiet, and Firstmate's own published comments should not be fed back as new user requests.
